# Monitoring research notes

## Vercel runtime logs

Official Vercel runtime logs documentation: https://vercel.com/docs/logs/runtime. Runtime logs include logs generated by Vercel Function invocations in Preview and Production deployments, including `console.log` output. Logs are shown in real time and grouped per request. The documentation states a maximum of 256 log lines per request, 256 KB per line, and 1 MB total per request. The Vercel dashboard Logs section supports filtering and inspection of runtime logs.

## Vercel environment variables

Official Vercel environment-variable documentation: https://vercel.com/docs/environment-variables. Variables can be scoped to Production, Preview, Custom, and Development environments. Environment-variable changes apply only to new deployments, so a redeploy is required after changing `GROQ_API_KEY`. Vercel states that variables are encrypted at rest and can be used during the build step or Function execution. The project should keep `GROQ_API_KEY` server-side and never expose it with a `PUBLIC_` prefix.

## Groq rate limits

Official Groq rate-limit documentation: https://console.groq.com/docs/rate-limits. Groq measures limits in RPM, RPD, TPM, TPD, ITPM, and OTPM. Limits apply at the organization level. The documentation lists response headers including `retry-after`, `x-ratelimit-remaining-requests`, `x-ratelimit-remaining-tokens`, and reset headers. A rate-limit breach returns HTTP 429, and the application should throttle and respect the response headers. The exact limits should be checked in the Groq account Limits page rather than hardcoded.

## Groq error codes

Official Groq error-code documentation: https://console.groq.com/docs/errors. Groq uses standard HTTP statuses. Relevant cases for this app include 400 invalid request, 401 invalid/missing authentication, 403 permission restrictions, 413 oversized request, 422 semantic/model request errors, 429 rate limit, 500 server error, 502 bad gateway, and 503 service unavailable. Error responses contain a structured `error` object with `message` and `type` fields. Retries should be reserved for transient upstream failures and 429 responses, with backoff and respect for `retry-after`.
